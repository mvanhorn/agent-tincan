# Trust model

## What Agent Tincan guarantees

- The relay only listens on your tailnet. The one exception is the optional MCP gateway (`--chatgpt-gateway`), which serves only the MCP tools, OAuth and, when you publish teammates in `a2a.json`, the [A2A](#a2a) cards and endpoints on its own Funnel hostname. It serves any cloud agent an admin connects with `tincan connect <name>` (ChatGPT, Sesame), each with its own tokens; each such agent's vendor receives the requests sent to it and every teammate answer it gets, including `history` and web-agent answers unless their allow files leave it out. `tincan connect` refuses a name already held by an agent joined from a real tailnet machine, so a gateway login cannot quietly take over that agent's identity; the admin must pass `--replace` to move the name to the gateway. Reconnecting a name that is already on the gateway needs no flag. The relay also polls AgentMail outbound for email replies (below); it never opens a listener for them.
- Push alerts are the one other thing that leaves the tailnet. When an admin phone turns on alerts on the [phone page](phone.md), its browser hands the relay a Web Push subscription: an endpoint at Apple, Google, Mozilla or Microsoft and the keys to encrypt to it. For each held ask the relay sends every subscription an encrypted alert that says only "A request is waiting for your approval" and how many are waiting: never the request text, the sender, the target or an id. The push service sees that the relay sent something to that phone, when, and the relay's VAPID contact (`relay@agenttincan.com`). The relay sends only to https endpoints on those four services, through no proxy, follows no redirect, refuses to connect to a private, loopback or tailnet address whatever a name resolves to, and gives up on a push after 10 seconds without touching the hold; a 404 or 410, or a 401 or 403 (the push service no longer takes the relay's VAPID key), drops the subscription, and one device keeps at most 5. Pushes go out in the background, so a slow push service never delays a send. The VAPID private key (`push-vapid-key`, 0600 in the state dir), endpoints and subscription keys are secrets: the audit log names a subscription only by its relay id. Without HTTPS on the tailnet a browser cannot subscribe, and the approval notify teammate remains the alert path.
- No web page can use the relay through a browser on your tailnet. A page open on an admin device would otherwise reach the relay with that device's tailnet identity, so the relay's tailnet listener checks every request before any route sees it. The request must name one of the relay's own addresses in `Host`: its MagicDNS short and full names, its tailnet IPs, or its `--listen` address (and, on the HTTPS listener for the phone page, its certificate name). That defeats DNS rebinding, where a page reaches the relay under the attacker's own name. When a request carries `Origin` or `Sec-Fetch-Site`, it must be same-origin. The one exception is `Sec-Fetch-Site: none` on `GET /phone/` (and on `GET /phone`, which only redirects there), which is the owner opening the page directly. A browser request that changes state must also be `Content-Type: application/json`, which no form can send. Every response forbids framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`). The CLI and MCP clients send no browser headers and use an address the relay advertises, so the checks never stop them. The checks cover the tailnet listener, not the relay's handler itself: the in-process MCP gateway and the local admin socket are not browser surfaces.
- The [phone page](phone.md) makes a browser on an admin device an admin client, and nothing more. The relay serves the page, every file it loads and the data it reads only to admin devices (the same WhoIs test as the CLI), and sends the page's files with a Content-Security-Policy that runs only the page's own script and fetches only from the relay. The page inserts agent names, good-at lines, request text and attachment names as text, never as markup. A browser approve or deny also needs a one-time nonce from the held list the relay sent that same device, bound to that request and decision and good for 10 minutes; the relay keeps only its hash, in memory, and never logs or audits it. Deciding therefore takes a fresh read of the held list from that same device, which a page from another origin cannot make. The held list hands nonces to every admin caller on the tailnet, not only to callers a browser marks, because over plain HTTP a browser's same-origin read carries no browser headers; a page from another origin is still refused, or cannot read the answer. Each decision is audited with the device's machine name. A tag on the phone, or its absence from `--admin`, shuts it out like any other machine.
- Every request is attributed to the agent that sent it, using Tailscale's identity for the machine it came from. An agent cannot send as another agent, and whatever it writes in the `from` field is ignored. The one exception is an email reply from an agent the owner opted in with `include_requests` (see Email replies below).
- Only admin devices and the relay's local admin socket can invite, remove, or connect agents, trace every chain, or upgrade the relay (`tincan relay-upgrade`). A caller is an admin device only when all of these hold: Tailscale WhoIs reports its short machine name in the `--admin` list; the node has no Tailscale tags; and, if `--admin-login` is set, the node's owning login is in that list. Machine names are chosen by whoever controls the node, so tag every agent machine (for example `tag:agent`): a tagged node is never an admin, whatever it is called. Owner login alone is not used, because on a single-user tailnet every node, agents included, has the same owner.
- Chains are tracked by the relay, not by the model. A request made while handling another continues that chain even if the model leaves the parent out. A request that would loop back to an agent already in its chain is rejected, and chains longer than 4 hops are rejected.
- A [scheduled ask](#scheduled-asks) gets every send check when it fires, not only when it is made. It starts a new chain, so it cannot be made while its asker holds a claim or has a guest's ask open.
- A session (`X-Tincan-Session`) is a routing label inside one agent, chosen by the client, not an identity. It decides which of the agent's windows a reply is handed to and which task a new ask is filed under. It never changes who the sender is, admin checks, rate limits, or wake content, and it never loosens a chain check: an ask filed apart from another session's task still carries that task's chain and hop. Any client of the agent can still read every reply by id or with a sessionless poll.
- A project label (`X-Tincan-Project`, and `project` on a send) is a routing label inside one agent, chosen by the client, not an identity. It decides which of the agent's windows is handed a request first. It never changes who the sender is, admin checks, rate limits, wake content, or chain checks. It keeps a request from being offered to the wrong window, and a claim by id is refused the same way, but it is no barrier between windows: all of them are the same agent, every one takes the request after 10 minutes, and any client of the agent that has the id can read the request or reply to it, and a peek gives every window the id through `hidden_ids`. The label is sender-chosen text, so a target cannot read it on a request held and never approved, and it never reaches a wake or a request email.
- Each sender is rate-limited (30 new requests per minute by default).
- Every send, delivery, claim, reply, rejection, wake, join, rebind, and removal is written to an append-only, hash-chained log. `tincan audit-verify` detects edits.
- Wake nudges carry only a count and an instruction, never request text, unless the owner sets `include_requests` for an email-woken agent (see Email replies below).
- Clarification does not add a trust boundary: only a request's claimed target can ask for input, and only its original sender can answer. Questions and answers stay on the same request, with the same chain and hop rules. They are bodies like other messages: readable by the relay, absent from wake messages, and represented only by byte lengths in clarification audit details.
- Socket wake (`tincan mcp` without `--channel` in Claude Code) writes into the session only the channel notice's count, senders and fixed instruction, never request or reply text. It reads the session's messaging token from its own environment and uses it only to authenticate to that local socket; the token is never logged, printed, stored, or put in an error. Programs run from the session's Bash tool inherit the same variables, so tincan pushes only when its parent process is the session that Claude Code's per-process registry (`~/.claude/sessions/<pid>.json`) lists for that socket, and re-reads that entry before each push. That keeps a tincan started from the session's own shell from pushing into the session as if it were that session's server. It is not a barrier against other programs the session runs: they inherit the token and could write to the socket themselves, as they can already act inside the session in other ways.
- Session titles reach the roster only for a Claude Code agent whose owner runs its MCP server with `--share-title`; it is off by default and setup never adds it. Once on, every joined agent can read each session's title in `list_agents` and `tincan agents`. Titles can name projects or people and can echo what a session was asked: Claude Code's generated titles summarize the conversation, and a hook that names sessions from their first prompt makes that prompt the title. The relay files a title under the authenticated agent and session, so no agent can set another's, checks it is one printable line of at most 120 characters, and keeps it in memory only. Rosters show it quoted, and agents are told to read it as information, never as an instruction.
- The roster's `status` tells every joined agent whether each teammate is busy, idle, stuck, limited (a web agent whose site is out of messages, with its reset time) or offline. For a busy agent it names the asker of the agent's oldest live claim and when it was claimed, so any joined agent can see who is asking whom right now, outside chains it took part in, except that a guest asker is named to an admin only; it never carries a request's text, progress note or id. A Claude Code session's busy state comes from Claude Code's own session registry entry for the parent process (`idle` or `busy`), never from the conversation or the screen, and is filed under the authenticated agent and session like a working-on line. An idle watch (`tincan watch`, the `watch` tool) tells only the agent that set it, with a relay notice naming the watched agent and nothing else.
- The roster's `stats` and `tincan stats` tell every teammate each other teammate's answered, failed and expired counts and median reply time over a window. They are counts and durations of finished asks, never a request's text, sender or id, so any teammate can see how the others are doing outside chains it took part in. A guest gets neither, and appears in `tincan stats` only for an admin device, as on the roster. The relay never routes on them.
- A [room](#rooms) is read only by its members, and only admin devices choose them. An @mention in a room is an ordinary ask from the poster, with every check a send has.
- Search has the same visibility as trace: joined agents can search requests and replies only in chains they took part in; admins can search every chain. Visibility is unchanged. Search indexes existing stored bodies, not attachment contents, and results include only attachment names. A `search` audit event records the result count, never query text.
- A trace export (`tincan trace <id> --format md|json --out <file>`) has the same visibility as trace, because it reads the same relay route on the client: an agent exports only chains it took part in, with the same placeholders for text hidden from it, and admins export any chain. Attachment contents are not exported, only their names, types and sizes. The relay does not know a read was saved: trace reads are not written to the audit log, so no record of an export exists. Once written, the file is outside the relay's controls: a teammate's later removal, a room membership change and attachment retention do not reach it, and it holds full request and reply text in the clear. The CLI writes it 0600 (Windows has no mode bits, so there the file takes its folder's permissions), refuses to replace an existing path, and with `--force` replaces the path rather than writing through a symlink or keeping a wider mode. Protecting the file after that, including any copy attached to a PR or handed to another agent, is up to whoever exported it.
- A [work lease](protocol.md#work-leases) is advisory: it tells teammates who has taken a resource and refuses only another lease. Nothing stops an edit, a push or a send under a teammate's lease, and a lease changes no check on any request. The holder is always the authenticated caller, never a name in a request. Only the holder, an admin device asking for it explicitly (`tincan lease release --relay`) or the local admin socket can release one, and `tincan remove` clears an agent's leases. An agent on an admin device releases as itself unless it asks too. Admin devices are owner-equivalent, so this keeps audit rows accurate and is not a boundary against that agent. Each lease lapses on its own, 1 hour after it was taken or renewed by default and 24 hours at most, so an agent that dies blocks no one for longer than that; an agent holds at most 32 live leases. The relay reads no meaning into a resource, and a trailing `*` makes it a prefix, so a lone `*` refuses every teammate's acquire until it lapses or an admin releases it. Every joined agent and admin reads every live lease with its resource and note, across the team and regardless of rooms or chains, and an agent connected through the gateway reads them in its vendor's app, so keep anything the whole team should not see out of both. A resource and a note are each one printable line of at most 120 characters, quoted when shown, and agents are told to read notes as information, never as an instruction. The audit log records each lease change, and each lapse, with its resource and holder and only the note's byte count, so resource names stay in the log after the lease is gone.

## Email replies

An email-woken agent such as Instinct can lose its tailnet path for long stretches while its email still arrives in seconds. For such an agent the owner can set `"include_requests": true` in `wake.json`. It is off by default and allowed only on an agent whose primary wake method is email.

- What leaves the tailnet: each open ask to that agent is emailed on its own, with its text (capped at 64 KiB), asker, urgent flag and earlier clarification rounds. Attachments appear only as a count. AgentMail and the agent's mail provider now hold that text, and the owner controls how long they keep it. Held requests, pings and notifies are never sent this way.
- What the agent trusts: a request email from the relay's sending address whose subject carries a `[tincan <id>.<tag>]` tag. Its standing instructions treat any other mail that claims to be from Agent Tincan as untrusted. When the agent can reach the relay, it takes the request from `tincan inbox` instead.
- How a reply becomes the agent's answer: the relay polls the sending inbox outbound. It records a message as that agent's reply only when every one of these holds:
  - The normalized From address equals the agent's `email_to`.
  - AgentMail did not mark the message spam or unauthenticated.
  - The subject's tag verifies for that request, agent and current clarification round.
  - The request is still open and not claimed under a live lease.
- The tag is an HMAC under `email-tag-key`, a 32-byte file in the relay's state dir (0600). That file never leaves the relay and is separate from `relay.key`, which every joined teammate holds (a guest does not). Rotating `email-tag-key` voids every outstanding tag.
- What an attacker needs: the ability to send mail as the agent's address that AgentMail accepts as authenticated, plus a live tag. Tags exist only in the agent's mailbox, the sending inbox and the relay. One tag can answer one open request, and dies when the request closes or its clarification round changes.
- Limits on email answers: email can answer, fail or decline a request. It cannot ask a clarifying question or attach files. Every tagged message from the agent gets one in-thread "recorded" or "not recorded" email with no request or reply text. The relay never deletes, marks or relabels mail, so other readers of a shared inbox see their mail unchanged. Audit rows record `via: email`, never the tag, the address or the text.

## Invitation storage and upgrades

The relay persists HMAC-SHA256 digests of one-time invitation codes, not the
codes themselves. The admin still receives a code once and `tincan join`
accepts it unchanged; existing clients do not need to upgrade together.

The HMAC uses a 32-byte relay-local `invite-pepper` file in `--state-dir`.
Keep this file private (0600) and preserve it when moving or restoring relay
state. A missing file is created on startup; if `relay.db` already exists,
the relay warns because a newly created key cannot redeem invitations minted
with a lost key. First upgrade from raw-code storage also creates this file.

Startup publishes a fully written, synced file without replacing an existing
winner, so concurrent initializers use the same completed key. On Linux and
macOS, existing keys are opened without following the final symlink, then
validated and read through that same file handle. Non-regular files, permissions
that allow group/other access, and lengths other than 32 bytes are rejected.
Other platforms currently fail closed rather than using an unsafe fallback.
A filesystem without hard-link support cannot perform first-time creation.

Upgrading invalidates outstanding legacy invitations; mint new ones after the
upgrade. Existing digest-shaped invitations survive reopening with the same
key. Agents, messages and the audit log are not reset. Deleting legacy rows is
not secure erasure of old SQLite pages, journals or backups. Do not run old and
new relay versions against the same state concurrently.

This is defence in depth for disclosure of the database **without** the key.
It does not encrypt messages or protect against access to both the database
and key, a compromised relay host, or another process running as the relay
user. Keep the state directory and its parents under the operator's control;
this is not a hostile-filesystem sandbox or a power-loss durability guarantee.

## Rebuilt machines

Rebuilding a sandbox or VM usually creates a new Tailscale node: a new stable node ID and IP under the same machine name, or that name with a `-1` style suffix if the old node has not expired yet. The relay re-admits such a machine as its old agent on its first call, with no new invite, when all of these hold:

- the new node has no Tailscale tags;
- its machine name matches the agent's recorded one, ignoring a trailing `-<digits>` suffix on either side, so `instinct`, `instinct-1` and `instinct-2` count as the same machine across rebuilds;
- it is owned by the same Tailscale login recorded for the agent. An agent with no recorded login is never re-admitted this way. Agents joined before logins were recorded get one on their first normal call from their own machine after the relay is upgraded; until an agent has made that call, a rebuilt machine needs a new invite for it;
- the agent's old node is offline or no longer on the tailnet, so two live machines can never share one agent;
- if the request names an agent (`X-Tincan-Agent`), it names that agent. When several agents lived on the old machine, each one moves only when it names itself, and until they all have, a request from the new machine that names no agent is refused as ambiguous rather than attributed to the one agent already moved.

If the relay cannot ask Tailscale whether the old node is online, the request fails with 503 and can be retried; it is not treated as a refusal.

This adds no new trust boundary. Tailscale already is the boundary: anyone who can add an untagged node owned by your login to your tailnet controls your tailnet, and joined agents trust each other fully anyway. The agent keeps its name, kind, and queued and claimed requests. Every re-admission is logged by the relay and written to the audit log as a `rebind` event with the agent, old node, and new node. Tagged machines are never re-admitted this way; they need a new invite. Start the relay with `--no-auto-rebind` to require an invite for every rebuilt machine.

## Attachments

- An attachment is uploaded by a joined agent and attributed to it like a request. It can be downloaded only by its uploader, the agents on the request or reply that references it, and admin devices.
- Limits: 10 MB per file, 8 files per message, 200 MB kept per agent and 1 GB relay-wide. Uploads are refused when the relay's free disk space would drop below 512 MB.
- Retention: an upload that no message references is deleted after 24 hours. Files on a message are deleted 7 days after its request is finished (answered, failed, declined, expired or cancelled); the metadata row stays, marked deleted, so traces still show what was sent.
- Like request text, attachments are readable by whoever runs the relay.

## The history agent

The `history` agent reads the owner's own conversations in ChatGPT, claude.ai, Grok, Gemini, Copilot, Codex, Claude Code, Grok CLI, Cursor (CLI and IDE), Copilot CLI, Gemini CLI and OpenCode. That is its whole job, so it is the most sensitive agent on the mesh, and its controls are built for that ([docs/adapters/history.md](adapters/history.md)):

- By default any joined agent may ask it. The owner can restrict that with an allowlist file (`~/.config/tincan/history-allow.txt`) of agent names. A file of names covers the whole request chain as the relay recorded it, not just the sender: if muse asks codex and codex asks history while handling muse's request, a file that lists codex but not muse declines it because of muse. The chain and sender come from the relay, never from the request body. A `*` entry means every joined agent. An unreadable allowlist or a bad name in it declines everyone.
- The access check runs in Go before any model sees the request. The only model step turns the question text into a structured query; it sees nothing else, runs with no tools, no MCP servers and a read-only sandbox, and its output is checked against a schema in Go. A request that is already a structured query (a `query:` first line and JSON) skips the model step entirely: the same schema and bounds are checked strictly in Go (one bare object, fields validated as sent), and a query that fails them is refused, never handed to the model.
- Retrieved chat content is never sent to a model by the history agent. Replies are filled in from a fixed template, so text inside the owner's chats cannot steer the service or anyone it answers. A pass is the one exception, and it is the owner's choice: `tincan pass` sends one chat to one web chat teammate, so that chat's title, earlier prompts' first lines and last 6 turns reach the destination's vendor and its model (see [Passing a conversation](#passing-a-conversation)).
- Only the owner sets how far back latest and search lookups go, with a window file (`~/.config/tincan/history-window.json`) or a flag on the local CLI. Nothing in a request can widen it. The window bounds only those lookups: a conversation asked for by its id is read whatever its age. A window file that is present but unreadable, malformed (an explicit null, a repeated key or trailing text included) or out of bounds fails every request until it is fixed, so a narrowed window never silently widens.
- Live reads go through the Tincan Chrome extension with the owner's existing session. The extension runs only its own fixed operations, including the seven argument-free `chatgpt.session`, `dots.session`, `claudeai.session`, `grok.session`, `gemini.session`, `perplexity.session` and `copilot.session` probes, and accepts nothing else; no cookie or token leaves the browser, and Chrome is never quit or restarted. The [session operation contract](../extension/README.md#session-operations) lists each probe's inputs and reads. Probes return only an empty success object or a typed error; empty Grok lists are indeterminate and cannot clear sign-out. Copilot's chat list and session probe open a tab: the extension opens copilot.com in a background tab of its own, reads the sidebar's chat links and titles for a list or checks the signed-in account gate for a session probe with fixed isolated-world functions, and closes it. It reads Copilot's rendered page there, never its tokens.
- Local reads stay on the owner's machine and are read-only. Besides Codex, Claude Code and Grok CLI, the service reads `~/.cursor/chats/*/*/` (`meta.json`, `store.db`), Cursor's `User/globalStorage/state.vscdb`, `~/.copilot/session-state/*/` (`workspace.yaml`, `events.jsonl`), `~/.gemini/tmp/*/` (`.project_root`, `chats/session-*.jsonl` and `.json`) and `~/.local/share/opencode/opencode.db`, or the same places under each CLI's home override, plus the wake lists `~/.config/tincan/*.wake-sessions` that mark wake runs to leave out. The Cursor and OpenCode SQLite databases, with their `-wal` and `-shm` files, are copied into a new 0700 temporary directory and read from the copy, never opened in place; the copy is deleted after every read, including one that fails. Nothing else in those homes is read: not the CLIs' configs, tokens or Cursor's other state keys beyond its `composerData:` and `bubbleId:` chat rows.
- Images it returns are relay attachments and follow the retention above.

By default any joined agent can read the owner's chat history. If some of your agents should not, write the allowlist file and keep it to agents you would trust with your history. Remember that an allowed agent that reads untrusted content can still be talked into asking. The allowlist governs requests to the history agent, not local shell access: an agent with a shell on the owner's machine (for example the Codex wake, which looks up prior threads with `tincan history codex`, or a gemini-cli or grok-cli wake, whose CLI runs shell commands with approval off) can read local Codex, Claude Code, Grok CLI, Cursor, Copilot CLI, Gemini CLI and OpenCode history directly, consistent with the full trust between joined agents.

## Passing a conversation

`tincan pass <chat> --to <web agent>` moves one of the owner's chats into a new chat on another web chat agent ([docs/adapters/pass.md](adapters/pass.md)). It is the one path that sends retrieved chat content to a model.

- Vendor egress. The chat is read through the extension like a history lookup, packed in Go with no model step into one message (title, each earlier prompt's first line, the last 6 turns verbatim), and typed into the destination's site as the owner. That vendor then holds that much of the chat under its own terms and retention, and its model reads it. The text sits between per-pass random delimiters with an instruction that it is material from another conversation, not instructions; that is an instruction to a model, not a control.
- Only the six web chat agents can be a destination, and only while signed in and not out of messages; anything else is refused before the chat is read. The seed is a grouped ask, so failover never carries it to a vendor the owner did not name.
- The seed is an ordinary relay request from the agent that sent it, so whoever runs the relay can read it, and the destination's allowlist applies.
- Agents' passes are held. An agent asks the `pass` service (`tincan pass serve`) to move a chat it names by URL or by source and id, never "latest". The relay holds every ask to an agent of kind `pass` for the owner's approval with no `approval.json` needed (a failed kind lookup holds), and `tincan held` shows the chat and destination parsed from the whole request. The service refuses to start unless the relay stores kind `pass` for it, so an older relay that does not know the kind never delivers passes unheld. Like history, it checks the relay-recorded chain and sender, in Go, against its own allowlist (`~/.config/tincan/pass-allow.txt`) and the history allowlist, and refuses a chat last updated outside the owner's history window. Nothing is read or sent before approval.
- The asker gets only the new conversation's id, never the chat's text. The seed continues the asker's chain, so the relay hides the seed's text and its reply from every agent but the seed's sender (the pass service) and its destination: a trace or get shows a placeholder, and search leaves the seed out. Admins still read both. Because any asker can continue a web chat by id, the destination web agent records every conversation a pass opened (`web-agent-<site>-passed.json`, 0600, ids only, shared by every web agent for the site) before the id goes out, and declines every asker's `conversation:` ask naming one, across restarts and from any agent for that site; a list it cannot read refuses every `conversation:` ask. The owner continues a passed chat in the browser. The service refuses a destination whose last-reported tincan build predates that refusal (a development build counts as older, since its contents cannot be told from its version).
- Local shells. The owner's `tincan pass` runs as the machine's joined agent, reads history through the local extension and is not held, so any agent with a shell on that Mac can run it, as it can run `tincan history`. The hold restrains asks over the relay, not local shells; that is the full trust between joined agents applied to a shell, as for council.

## The web agents

The `chatgpt-web`, `claude-web`, `grok-web`, `gemini-web`, `perplexity-web` and `copilot-web` agents act as the owner in ChatGPT, Claude, Grok, Gemini, Perplexity and Copilot: whatever an allowed agent (by default, any joined agent) asks is typed into the owner's logged-in account, uses the owner's plan, lands in the owner's chat history, and can draw on that account's memory and custom instructions ([docs/adapters/web-agents.md](adapters/web-agents.md)). The answer goes back to the asker, and that answer can include what the site remembers about the owner.

- By default any joined agent may use them, so any agent on your mesh can act as you in ChatGPT, Claude, Grok, Gemini, Perplexity and Copilot. To restrict that, write an allowlist file (`~/.config/tincan/chatgpt-web-allow.txt`, `claude-web-allow.txt`, `grok-web-allow.txt`, `gemini-web-allow.txt`, `perplexity-web-allow.txt`, `copilot-web-allow.txt`) of agent names. A file of names covers the whole relay-recorded chain, as for history, so relaying through an allowed agent never widens access. An unreadable allowlist or a bad name in it declines everyone.
- The message is data. The extension passes it as an argument to a fixed function in an isolated content script and inserts it as text; nothing in a message or a page is executed. The extension still accepts only its fixed operation set. Text send operations take only a message capped at 32 KiB of UTF-8, an optional validated conversation id and a boolean. The registered image-input operations are `chatgpt.input_begin`, `chatgpt.input_chunk`, `chatgpt.input_abort` and `chatgpt.send_images`; their compiled per-site gate is currently off for every site in both Go and the extension.
- Image input uses a separate payload: begin takes file metadata, chunk takes an opaque transfer token, sequence and base64 data, abort cancels the transfer, and send_images consumes the token once alongside the usual send arguments. Only one to four nonempty PNG/JPEG files are accepted, at most 10 MiB each and 20 MiB total, in ordered chunks of at most 96 KiB decoded. Go validates decoded pixels and MIME agreement, rejects animated PNG and caps each image at 40 million pixels. Names are nonempty UTF-8, at most 255 bytes, without control characters or path separators. No URLs, file paths, selectors or scripts are accepted. The worker verifies complete byte counts and SHA-256 checksums.
- Image transfers are bound to the native connection and site; the host assigns connection identity and rejects service-supplied identities. Failure or disconnect aborts the connection's transfers, but cannot delete vendor uploads. The worker caps reservations at four concurrent transfers and 40 MiB of decoded bytes, including queued and active sends; cancelled active sends keep their reservation until cleanup finishes. Unconsumed transfers expire after two idle minutes or ten total minutes.
- The extension opens and closes its own background tab and never scripts a tab the owner opened. It checks the site session before opening a tab, so a logged-out browser never sends anonymously; a session probe redirected to another host's sign-in page counts as logged out. Copilot has no session check the extension may call without a token, so its send tab is the gate: nothing is typed unless the tab stays on copilot.com and shows a signed-in account, and a tab sent to a Microsoft sign-in, terms or work-account page, or to any host whose address Chrome hides from the extension, is logged out.
- The extension acts on a site only while Chrome grants it that site's page origins, checked before every operation except closing its own tab and aborting an image transfer. Sites beyond ChatGPT and claude.ai (Grok: grok.com and its image host assets.grok.com; Gemini: gemini.google.com and its image host lh3.googleusercontent.com; Perplexity: www.perplexity.ai; Copilot: copilot.com and copilot.microsoft.com) are optional host permissions the owner grants from the extension's options page (a packaged extension page, no inline script, never in a site's page); revoking one stops every operation for that site at once.
- Reads are fixed JSON requests from the extension's service worker. grok.com's image URLs are looked up by the extension from the conversation itself (by response id and index) and fetched only from grok.com's own hosts; no URL travels from Go or a request to the extension.
- Gemini reaches further than a chat. Its answers can draw on the Google apps connected to the owner's account (Gmail, Drive, Calendar), so any agent allowed to ask `gemini-web` can read that data through it. Setup recommends a `gemini-web` allowlist (`~/.config/tincan/gemini-web-allow.txt`) of only the agents that should, or disconnecting those apps in Gemini.
- Gemini is read through its app's own `batchexecute` endpoint from the extension's service worker, with fixed rpcids and payloads; the page's session values stay in the worker's memory and are never returned. Its images are fetched by response and position, never by a URL from the socket, and only from `lh3.googleusercontent.com`, first inside the extension's own send tab (isolated world) and then from the worker. Nothing runs in a page's main world.
- Account risk: Google's terms prohibit automated access. The `gemini-web` agent acts as the owner, on the owner's own account, at a human pace, but that is the owner's decision to make, and Google's enforcement can reach the whole Google account, not only Gemini.
- Perplexity serves signed-out visitors a working message box, so a sign-in redirect proves nothing there. `perplexity.send` opens no tab until `GET /api/auth/session` names a signed-in user with an id, and the send tab checks the page for a sign-in link again before typing, so `perplexity-web` never asks anonymously. The session answer is only checked; its fields are never returned or kept. Thread reads are fixed `GET /rest/thread/<slug>` requests from the service worker that return only the entry fields the Go side reads, so the thread's `read_write_token` never leaves the extension. The reply is read from that JSON, never from the page, and nothing runs in a page's main world. Perplexity is not a history source.
- Account risk: Perplexity's terms do not allow using the service by automated means. `perplexity-web` acts as the owner, on the owner's own account, at a human pace, with a cooldown after a rate limit or a Cloudflare challenge; Perplexity can still limit or suspend the account, so the owner turns it on knowingly (its setup says so). Its replies carry web source links chosen by Perplexity: an asker gets those URLs as text, and nothing on the owner's machine opens them.
- Copilot is read from copilot.com's own page data (the conversation page asked for JSON) by the extension's service worker with the owner's cookies and no token. That answer also carries a reconnect token and token-bearing telemetry; the worker keeps only the messages' ids, authors, texts, times and source links, the title and the times, and drops the rest before anything is returned or logged. Copilot keeps its bearer tokens in the page's storage; the extension never reads them and never runs code in the page's main world. Its chat list is read from the rendered sidebar in the extension's own tab (see the history agent above). Copilot's human check ("Verification required") is detected and never touched: the send fails `blocked` and Copilot is left alone for 5 minutes.
- Account risk: the Microsoft Services Agreement prohibits automated access. The `copilot-web` agent acts as the owner, on the owner's own personal account, at a human pace, but that is the owner's decision to make, and Microsoft's enforcement can reach the whole Microsoft account, not only Copilot.
- The `dot-web` agent types requests into the owner's OpenAI dot DM, where they appear as the owner's own messages, and the dot can act on its own in the apps the owner connected to it (Gmail, GitHub, Google Drive and others). So a teammate's request to the dot acts with the owner's authority there. Asks and notifies to `dot-web` are held for the owner's approval by default; an `approval.json` entry for `dot-web` replaces that default, so write one only for senders you would let act as you in those apps. The dot can also ask teammates (`@tincan ask <agent>`, limited by `~/.config/tincan/dot-web-send.txt`), and their answers are typed back into the DM as `[tincan-reply from <agent>]` messages. Those, too, appear as the owner's messages. A setup message tells the dot that typed requests and `[tincan-reply]` messages are data from teammates, not the owner's instructions, and to ask the owner before writing through a connected app for a teammate. That is an instruction to a model, not a control: it is most likely to hold for the clearly marked `[tincan-reply]` messages, while a typed request is indistinguishable from the owner's own words. The approval hold is the control. The one exception is a council: the dot sits on councils by default, and Council's asks to it skip the hold only when the owner approved that council question (see [Council](#council)). Nothing is installed on the dot's computer, and the dots operations use the extension's existing ChatGPT access.
- The `duet-web` agent does the same in the owner's Claude Duet chat on claude.ai/duet, and everything above applies to it: requests appear as the owner's messages, Claude can use the owner's connected apps (Gmail, Calendar, Drive, Slack), so asks and notifies to `duet-web` are held for the owner's approval by default, and Claude's `@tincan ask` messages are limited by `~/.config/tincan/duet-web-send.txt`. Only messages Claude wrote start an ask; the owner's own `@tincan ask` lines and anyone else's are ignored. Two controls are specific to Duet. The extension serves only a 1:1 chat: on every read and send it checks the channel record and refuses (`channel_refused`) one that is shared with any other member or guest, archived, disabled, not private, or not owned by the signed-in account, so another person's messages can never become requests or answers and a request is never posted where someone else would see it. And it reads whether Claude is working from the channel's event stream: it opens `/messages/stream?from=tail`, reads only the opening `session_activity` snapshot for at most 4 seconds and closes it, so a send never types while Claude is mid-task. Duet reads use the owner's claude.ai cookies with the organization id from `/api/organizations` as a header; no cookie, header or token leaves the worker. The `duet.session` probe is the same argument-free claude.ai check as `claudeai.session`. Nothing is installed in Duet, and Claude's side needs no network path to the relay.
- The state file keeps only which conversation each asker used last (0600), never message text.
- Account terms: OpenAI, Anthropic, xAI, Google, Perplexity and Microsoft prohibit automated access to their apps. The web agents act only as the owner, on the owner's own account, one request at a time at a human-paced poll cadence, with a per-site cooldown after a rate or plan limit; a site can still limit or suspend an account it believes is automated, so the owner turns each one on knowingly (the grok-web, gemini-web, perplexity-web and copilot-web setups say so).
- The site's answer is untrusted content: the web agents reply with it as is. An agent that acts on a web agent's answer is reading model output, with the risk described below.
- Failover sends an ask to a vendor the asker did not pick. When a web chat agent's site is out of messages, the relay moves an ask nothing has typed yet to another of the six web chat agents (never `dot-web` or `duet-web`), so its text goes to that agent's vendor (for example Google instead of Anthropic) under that site's terms and retention. The asker is told at once which teammate took it. The owner keeps asks off a web agent by listing it in `failover.json` in the relay state dir; an unreadable or invalid file fails closed, so no ask moves until it is fixed, and the problem is logged. Failover only picks a teammate whose last report says it is signed in. A move is checked again against the new target's approval gate, default kind holds and the chain's loop and hop rules, and a move that would be held is refused, so failover never reaches a target the owner gates. The new target's own allowlist still applies when it handles the ask. An ask never moves when it is to or from `dot-web`, `duet-web` or a council, was ever held for approval, is a notify, is grouped, carries attachments, names a conversation, has a clarification exchange, is a follow-on, or may already have been sent, so failover cannot carry approved, council, attached or forwarded material to another vendor. Only the relay moves an ask; a request body cannot name its own target or `moved_from`.
- A move changes a request's target, the first relay path that does. Every write keyed by request id (claim, reply, needs input, progress, email reply) also checks the target, so the old target cannot answer, claim or read the request once it moved, and it drops out of that agent's search and trace. Each move is an append-only `moved` audit event with ids, from, to and reason, never the text.
- Handback. A web agent hands back an ask it claimed and did not send (`POST /v1/requests/{id}/handback`) instead of failing it; only the claimant under a live claim may, and its reset time is capped at the limit the same agent reported. The relay cannot prove the ask was not typed; a web agent's host could already misuse any ask it claims, so a handback adds no trust. A limited agent's own limit reports come only from its authenticated identity, like its sign-in reports.
- Limit detection reads the page's alert and status text after a send, in the extension's own send tab, as text only (the same isolated content script), and returns at most 500 characters with the send's result. Go matches it against fixed per-site patterns; the text is never shown in a reply, logged, sent to the relay or passed to a model.

## Command-woken CLI agents

The `codex`, `gemini-cli`, `grok-cli`, `copilot-cli` and `cursor-cli` teammates are coding agents that `tincan listen --exec` starts headless whenever requests are waiting. The first three run with tool approval off, so a teammate's request can run commands on that machine with no one confirming them, which is the full trust between joined agents applied to a shell. The copilot-cli and cursor-cli wakes keep approval on instead (see below). Both need a relay from this release to be invited with their kind.

- A wake starts its CLI wired only to its own teammate. The gemini-cli and grok-cli wakes (both on the shared wake library, `examples/lib/tincan-wake-lib.sh`) read the CLI's own MCP configuration before each run and refuse to run unless there is exactly one agent-tincan server, pinned to the wake's own `TINCAN_CONFIG`, and no other server the operator has not allowed. The grok-cli wake also runs Grok with a home of its own (`HOME` and `GROK_HOME`), so Grok's import of the owner's Claude Code and Cursor MCP servers finds nothing, reads Grok's listing with `grok inspect --json`, and refuses plugins and hooks too. That guards against misconfiguration, not against the model: a CLI with a shell can still run `tincan` with another co-located agent's `TINCAN_CONFIG` and act as that agent. Allowlists that name agents (such as the history allowlist) keep agents apart only when they run on different machines. A wake that cannot run (identity mismatch, missing or expired login, missing API key, repeated failures) backs off, leaves requests queued, and tells the operator teammate once.
- Writes are confined by the CLI's own sandbox where it has one. Codex runs in its `workspace-write` sandbox. The gemini-cli wake's Gemini CLI engine runs in its `--sandbox` (seatbelt on macOS), writing only in its working directory and the write roots the operator opened; Gemini CLI's documented default profile (`permissive-open`) also allows writes to temp and cache directories, and this wake has not verified that list. Grok runs in a sandbox profile the wake writes before every run, `tincan-wake`, which extends Grok's `workspace` profile (Seatbelt on macOS, Landlock on Linux): it writes only in its working directory, temp directories, its own Grok home (where Grok keeps its config, sandbox and hook files write-protected) and the directories the wake opens: the teammate's attachments folder and the operator's write roots. Every wake canonicalizes the write roots and checks them against allowed roots, and Grok refuses to start when it cannot apply a custom profile. Reads are unrestricted and the network is open in all of them. See [docs/adapters/gemini-cli.md](adapters/gemini-cli.md) and [docs/adapters/grok-cli.md](adapters/grok-cli.md).
- The copilot-cli and cursor-cli wakes keep tool approval on and allow only the Agent Tincan tools, so in headless mode any other tool call is denied rather than prompted. Copilot runs in a `COPILOT_HOME` of its own with the built-in GitHub MCP servers off (`--disable-builtin-mcps`), one `--allow-tool 'agent-tincan(<tool>)'` per Agent Tincan tool, and `COPILOT_ALLOW_ALL` cleared from its environment; the wake never passes `--allow-all-tools`, `--allow-all` or `--yolo`. Cursor runs with `CURSOR_CONFIG_DIR` set to a private directory in its wake home, so the owner's `~/.cursor` (its `cli-config.json` allow entries, `mcp.json` servers and hooks) does not apply to wake runs, and the wake's chats are kept there rather than in `~/.cursor`. The wake rewrites its workspace's `.cursor/mcp.json` and `.cursor/cli.json` before each run, so only the agent-tincan server loads and only `Mcp(agent-tincan:<tool>)` entries are allowed, and passes `--approve-mcps --trust` but never `--force` or `--yolo`. Because `--approve-mcps` also approves every server in the private directory's `mcp.json`, the wake refuses to run while that file names any other server not listed in `TINCAN_WAKE_ALLOWED_SERVERS`, and it refuses a `hooks.json` there or in the workspace. Neither CLI has a watchdog of its own: both rely on the shared wake library's run timeout (`TINCAN_WAKE_TIMEOUT`), which stops a hung run and everything it started. See [docs/adapters/copilot-cli.md](adapters/copilot-cli.md) and [docs/adapters/cursor-cli.md](adapters/cursor-cli.md).
- Antigravity (`agy`, the gemini-cli default engine) documents no sandbox. The wake runs it only when the owner sets `TINCAN_GEMINI_ALLOW_UNCONFINED=1`, and then nothing limits its writes to the owner's files.
- Secrets in the environment reach the model. The Gemini CLI engine needs `GEMINI_API_KEY` in its environment, and an `XAI_API_KEY` in the grok-cli listener's environment is there too; like any other variable there, a command the model runs can read it and, with the network open, send it anywhere. So can the Grok login in the wake home (`.grok/auth.json`), which the run needs to read.

## Per-request workers

`tincan listen --exec <cmd> --per-request` starts one fresh process for each ask, with nobody watching ([README](../README.md#one-process-per-request)).

- The owner's flag is the only way in. No request, teammate or relay setting can turn this mode on, change its command, or choose its repository. Only whoever starts the listener decides that.
- Unattended, by design. Each ask starts a process at once, with no one confirming it, the same trust as a command-woken CLI agent. A teammate's request becomes a process running the owner's command on this machine. What that process may do is whatever the command allows, so a command that starts a coding agent with approval off gives a teammate a shell, as in [Command-woken CLI agents](#command-woken-cli-agents).
- It runs as the listening agent. A worker has no identity of its own: it uses the listener's `TINCAN_CONFIG` and every other variable in the listener's environment, secrets included, and the relay sees its calls as that agent. `TINCAN_SESSION` is a routing label as described above, never an identity. Workers on one listener can read each other's replies and act for each other, and they are not separated from each other or from the machine's user. A git worktree separates their files by convention only, not by any sandbox.
- The request is data. Its body reaches the process on stdin and never through the shell, and `TINCAN_REQUEST_ID` and `TINCAN_FROM` come from the relay. The body is still a teammate's words, with the risk described below, and a process that passes it to a model passes that risk on.
- `TINCAN_FROM_GUEST=1` is set on a request a guest's ask led to, and comes from the relay's mark. It does not tell an ask the owner approved from one nobody approved, such as one from a `--no-hold` guest, and neither the environment nor stdin says which it is. A command that acts on the variable has to treat every marked request as outside input.
- Limits are the operator's flags. `--max-workers` caps concurrency, and every queued ask beyond it waits. `--timeout` kills the worker's process group, and a worker's exit kills what it left running there; a child that moves itself to another group or session escapes both. The relay's send rate limit, approval holds, chain rules and allowlists apply to a worker's asks as to any others from this agent. A hold on an ask to this agent runs before the listener can see it, so the listener never starts a process for a held request.
- The inbox is agent-wide. Workers share the agent's queue, so `tincan inbox`, or a `check_inbox` from a `tincan mcp` a worker starts, takes asks past `--max-workers` and shows a worker its siblings' claims. Nothing stops a worker doing that, so keep them to `tincan reply`.
- The listener reads a worktree without trusting it. A worker can rewrite the tree's `.git` file, so the listener checks the tree with the git directory it recorded before the worker ran, and a sandbox confined to the tree stays confined when the listener runs git afterwards.
- A kept worktree stays on disk. One with uncommitted changes or new commits stays under the config directory until the owner removes it, and it can hold whatever the worker wrote there.

## Council

The `council` agent puts one question to every model on the team, has them rank each other's answers blind, and has a chairman write the verdict ([docs/adapters/council.md](adapters/council.md)). It is a Go service, not a model, but it is the one agent whose whole job is to send your text to several outside vendors at once.

- Vendor egress. Each web member types its prompt into its vendor's site as the owner. That prompt carries the question and any inlined attachment text, and in the review and chairman stages it also carries every other member's answer. A council with ChatGPT, Claude, Grok, Gemini, Perplexity and Copilot sends all of that to OpenAI, Anthropic, xAI, Google, Perplexity and Microsoft, under each site's own terms and retention. Command-woken CLI members send it to their model's API the same way.
- Memory-informed answers reach other vendors. A web member answers from the owner's account, so its answer can draw on that site's memory, custom instructions and, for Gemini, connected Google apps. During review that answer goes to every other member's vendor. Something Gemini knows from Gmail can end up in the prompt Council sends to ChatGPT.
- Held by default. The relay holds every ask to an agent of kind `council` for the owner's approval, with no `approval.json` needed, and a failed kind lookup holds rather than delivers. `tincan held` shows the target kind and each attachment's name and size, so the owner sees what would go to vendors before approving. An explicit `approval.json` gate entry for the council agent replaces the default; `{"from": []}` turns the hold off. The hold is by target, so an agent's leaderboard read is held too. `tincan council serve` refuses to run unless the relay stores kind `council` for it, so an older relay that cannot hold councils never runs one.
- Approval from an admin device is owner-equivalent. `tincan approve` and the owner's `tincan council "question"`, which approves its own held request when run interactively in a terminal on an admin device, are the owner acting. The hold restrains agents only because they cannot approve: an agent with a shell on an admin device, or on the relay host with access to the admin socket, can approve its own council. Keep agents off admin devices if the hold should mean something. `tincan council` approves its own request only when its stdin and stdout are both terminals on an admin device; otherwise it waits for approval like any ask. That check is not a security boundary, since an agent can run the command under a pseudo-terminal. It does not need to be one: an agent with a shell on an admin device can already approve its own requests with `tincan approve`. The default hold restrains the agents that cannot approve.
- Council asks to the dot. The owner's OpenAI dot (`dot-web`) sits on councils by default, and it acts with the owner's authority in its connected apps. Council's answer, review and chairman asks to the dot skip the dot's default hold only when their parent is a council question the owner approved, either with `tincan approve` or by running `tincan council` in a terminal on an admin device. Every other ask to the dot is still held, and `approval.json` gates still apply. So approving a council question also lets it, and in review every other member's answer, reach the dot. To keep the dot off councils, add `dot-web` to `exclude` in `council.json`; a council form can still name it, but that convening ask is itself held for the owner. Blind review strips the dot's DM footer, its attachment and delegation notes and its `@tincan ask` paragraph so reviewers cannot tell which answer is the dot's. Claude in a Duet chat (`duet-web`) is treated the same way: its asks skip the hold under the same rule, and blind review strips its `your Duet channel:` footer, notes and `@tincan ask` paragraph. To keep it off councils, add `duet-web` to `exclude`.
- The chain never widens. The convener and every agent in its chain never sit on the council or chair it, and allowlists and approval rules apply to Council's member asks through the chain as usual. A form may name only web and wakeable model teammates or agents the owner listed in `council.json`, never a service such as history or notes, so their retrieved content does not reach a vendor through a council.
- Answers are untrusted content. Reviewers and the chairman see answers between per-council random delimiters with an instruction that the enclosed text is material to judge; only the defined output fields are parsed, and the chairman cannot change the peer scores. The reply is still model output: an agent acting on a verdict is reading model text, with the risk described below.
- Retention. Inlined attachment text lives in request bodies, which the relay keeps like any other request, not on the 7-day attachment clock. Council's database and reports stay in its folder on the owner's machine (0700 folders, 0600 files) until the owner deletes them. The report and scorecard are local files; nothing is hosted.

## Follow-on asks

`tincan ask muse "..." --then hermes "file the receipt"` (the `then` param on `ask`) queues one ask that the relay sends when the first is answered, with the reply in its body ([protocol](protocol.md#follow-on-asks)). No model turn sits between the reply and the send, so these are its limits:

- The asker authorized it at send time. The relay sends it as the asker, without asking again. The owner sees the follow-on's target and text with a held first request (`tincan held`, the phone page), and a held follow-on's whole body, reply included. A listing has room for about 3 MiB of this text. What does not fit is cut with a note, and the relay refuses to approve it until older requests are decided and the listing shows it whole.
- A reply reaches a third teammate. Whatever the first target answered goes to the follow-on's target and, for a web or CLI teammate, to that vendor, and is stored in a request body like any other: readable by whoever runs the relay, and searchable by agents in the chain. The follow-on's target joins the chain, so `trace` shows it the first request and its reply too. A held target joins only when the owner approves: until then, and after a denial, its trace and search stay as if it had never been asked.
- The wrapper is an instruction to a model, not a control. The reply sits between per-follow-on random delimiters with a fixed line calling it a teammate's reply and data, not instructions. The nonce keeps a reply from closing the delimiters, whether it forges them or an answered-by line. It does not stop a model from following text inside them, and the target's standing instructions otherwise treat a teammate's request as authorized. A first target that reads untrusted content can pass that content on this way, with the risk described below. If a target can act on what it reads, hold it with the [owner approval gate](#owner-approval-gate). The hold is the control.
- Approval does not carry over. Holds treat a follow-on as having no parent, so an approved ask to a council followed by `--then dot-web` leaves the follow-on held for the owner, unlike the council's own asks to the dot. `approval.json` sees the whole chain, and approving the first request approves nothing that follows it.
- Chains stay relay-tracked. A follow-on takes the first request's trace, hop plus one, and the first request's chain plus its target, so the loop and hop rules see both. It takes a slot of the asker's rate. A refused follow-on is dropped and the asker gets a notice. The path that accepts an answered, already-closed request as a parent is a relay-only field. A client that names an answered request as `parent_id` is still refused.
- Private services stay out. `then` is refused when the first target's kind is `history`, `notes` or `pass`, the same list that keeps them out of rooms, and the fire checks the kind again, dropping the follow-on with a notice that carries no reply text, so a kind changed after the send cannot forward what those services retrieve. A kind the relay cannot read leaves the follow-on waiting. This looks only at the first target: a teammate that fetched such data and put it in its own answer forwards it like any other reply.
- A follow-on goes only where it was sent. It never fails over, since its body carries a teammate's reply to a vendor the asker named. Attachments are never carried.
- Fired once. The row is marked due in the reply's transaction and deleted in the transaction that enqueues the follow-on or its notice. Only an answered reply fires it. A request that ends any other way drops it, and a removed asker's follow-on is dropped unsent.
- The audit log records `follow_on_sent` and `follow_on_dropped` with ids, names and a reason, never text.

## Guests

`tincan invite friend --guest --ask muse,instinct --for 3d` lets someone outside the team ask the teammates you list, until a set time of at most 30 days. Tailscale is still the boundary, and a guest is a new kind of caller inside it, so this section says what the tier gives you and what it does not.

What the relay enforces:

- A guest only asks. A wrapper in front of every route refuses a guest unless the route is on a short list, so a route added later is closed until someone opens it ([protocol](protocol.md#guests)). No teammate can be sent work by way of a guest, and nothing but the relay's own notices reaches one.
- A guest reaches only the teammates you listed. Its send takes `to` and `body` and nothing else: no `--then`, no attachments, no group, no urgent, no parent. Any other field is refused, including one added later. Its roster shows the listed teammates and a few facts about each, and failover never moves its ask to a teammate you did not list. Its asks can never go to a phone, a guest, or the history, notes or pass services, since those read your private data.
- A guest's ask is held for you by default, with its whole body shown in `tincan held`, where control characters print as their codes so a body cannot hide from you what would be delivered. An `approval.json` entry cannot lift that hold. `--no-hold` can, for one guest, and the invite's audit row records it. It lifts only this default: `approval.json` and the holds on council and the web agents still apply.
- What follows from a guest's ask stays marked. A teammate working on one sends with the mark, however the request finds its parent, and a body line says so for clients that ignore the field. What a guest wrote also sits between per-request random delimiters with a fixed line saying whose text it is, so it cannot close the request block and pass for a teammate's request. Those delimiters are an instruction to a model, not a control. A marked request never goes out as a request email: it would carry none of this framing, and the claim the mark follows would never be made. It arrives as a count and is read through the inbox. While that work is unapproved, including all of a `--no-hold` guest's, the next ask is held for you too. Agents' standing instructions say an unapproved marked request is outside input, not owner-authorized work.
- A guest holds no relay key. `relay.key` is how a teammate recognizes the relay after it moves, so whoever holds it could pass as the relay to an agent looking for it. Every joined teammate holds it, and a guest does not. That also means a guest cannot find a moved relay on its own and needs the new address from you.
- A guest needs `--admin-login`. The relay refuses a guest invite without it, because without a login check the name of a machine would be all that made it an admin device, and a guest names its own machines. A machine carrying a guest is never an admin device, whatever its name or login.
- A guest invite is new-only, so a code cannot take a teammate's name, and a guest's name cannot become a teammate's without `tincan remove`. Guests are never re-admitted to a rebuilt machine; invite them again.
- The term ends on time. From `guest_until` on, every route answers 403, before any sweep runs, and a send or answer whose body was still arriving is refused once it is read. The sweep then cancels its open requests and audits `guest_expired`. A long poll already in flight can finish up to one poll hold later and can carry a reply that landed in that time.

What it does not do:

- An ask you approve is then ordinary work. The teammate acts on it as it would on your own request, and asks others on that basis. Read it the way you would read mail from a stranger with a request in it: `tincan held` shows the whole body, and approving is the review. The mark stays on so you and the teammate can see where it came from.
- An answer to a teammate's needs_input question from a guest is not held for you, or the round trip could not finish. You approved the ask, not the answer, so the request stops being approved when a guest answers: the teammate reads it as outside input again, and what it sends next is held.
- Rate limits are the only limit on how much a guest sends. It can fill your held queue, and your alerts, at the 30 asks a minute any sender gets. `tincan remove` cuts it off.
- The mark follows requests, not information. A teammate's reply to a guest can carry anything that teammate knows, and work outside a marked request, such as a post to a room, is not marked. Keep a listed teammate's reach in mind when you list it.
- Sharing the relay machine shows a little to everyone on the guest's tailnet account. The share is to an account, not to one machine, and a shared-in machine can reach `/v1/hello`, `/v1/dist` and `POST /v1/join` without being joined. They answer with a proof that this is the relay and with your release files. Invite codes still decide who joins.
- A second guest cannot share a machine with the first, and a guest cannot share one with a teammate. A guest code redeemed on your own admin device makes that device lose admin status. The local admin socket on the relay host still works, and `tincan remove` frees it.
- The relay does not know a guest's account beyond its Tailscale login, recorded on join. Sharing is done in the Tailscale admin console, and stopping the share there is the other way to cut a guest off.

## A2A

A2A lets a client on the open internet ask a teammate you chose, over the gateway. It is off until you turn it on, and it needs three things: a relay started with `--chatgpt-gateway`, a 0600 `a2a.json` in the relay's state directory naming a teammate, and a guest made with `tincan connect <name> --guest`. See [docs/a2a.md](a2a.md).

What holds:

- An A2A client is a guest, and gets a guest's limits and nothing more. The gateway keeps no rule of its own that widens anything. Each A2A call becomes a relay call from that guest's own name through the relay's own handler, so the route allowlist, the send field check, the hold, the mark and the term all apply on every call ([Guests](#guests)). A token that is not a guest's is refused.
- `a2a.json` grants nothing. It says which teammates have a public card and an endpoint. Whom a client may ask comes only from the guest's `--ask` list, so a teammate must be both published and listed. Without the file, or with a file that is malformed, not a regular file, or readable by anyone but its owner, nothing is published and the routes answer 404. The file is read on every call, so removing it turns A2A off without a restart.
- A gateway guest is always held. `tincan connect` has no `--no-hold`, and the relay refuses one, because the caller is on the open internet with no Tailscale account behind it.
- A gateway guest is a new name only. It cannot take a teammate's name even with `--replace`. To give one a new login, run `tincan remove` and connect it again.
- A gateway guest gets A2A and nothing else. Its token is refused on `/mcp`, whose tools are written for teammates.
- Cards show the name and description from `a2a.json`, and nothing from the roster. The relay's agent API stays off the public side. In particular the gateway has no route to `GET /v1/hello`, and a task id cannot be steered to one: an id must look like an id, and stays inside one path segment. So an A2A client cannot fetch the relay's hello proof and pass it off to a teammate looking for a moved relay. A guest on the tailnet still can fetch that proof, since hello is open to it.
- A task belongs to the guest that sent it and the teammate it went to. Any other id is not found.
- A client can cancel a task only until a teammate has been given it. The relay refuses to cancel a claimed request, and for a gateway guest also one that was claimed before or whose question was answered, even when it is back in the queue. The gateway also refuses a delivered one. Otherwise a client could drop the mark while the teammate acts on what it read, right after answering a question you never saw. Two gaps remain. The check reads the task and then cancels it, so a delivery landing between the two can still be cancelled. And a request delivered but never claimed goes back to the queue when its delivery lease runs out, and a client can cancel it then; the teammate never had a claim on it, so this is the read-but-not-claimed case below. A guest on the tailnet can cancel a delivered or requeued request, as a relay note may tell it to; only a gateway guest is refused.

What it does not do:

- Anyone who holds the token is the guest. A guest on the tailnet has a Tailscale login behind it. A gateway guest has only the one-time code, then OAuth tokens, so whoever gets those can act as it until the term ends or you run `tincan remove`. The relay records no account for it. A login code is good for 10 minutes and one use. The login page locks for everyone after five wrong codes in ten minutes, so a stranger can keep it locked.
- Cards are public. Anyone can read the names and descriptions you publish, with no token. Write descriptions for the open internet. Clients may cache a card for 5 minutes.
- The mark does not cover everything that follows from a client's task. A request a guest sent keeps its mark for good. What a teammate sends is marked only while it holds an open claim on marked work, or while it names a marked request as its parent. So what the teammate sends is not marked, and not held, in these cases:
  - after it has replied, if it keeps working. This is the common one.
  - while its own question waits, from a needs_input reply until the client answers and it claims the request again. Once it claims again it is marked and held as before.
  - after you run `tincan remove` or the guest's term ends. Both cancel a claimed request, and the teammate may not know yet. A client can see its term coming, but cannot cause this at a time of its own choosing.
  - after a claim's lease runs out and before the request is claimed again.
  - in a request it read but has not claimed. `check_inbox` claims at once, so the gap is short.
- The mark follows requests, not information. Text from a client that a teammate saved, posted to a room or put in a file carries no mark, and a later session reading it is not marked. A teammate's reply can carry anything it knows, and over A2A that reply leaves your tailnet. List a teammate only if you are happy for an outside client to read what it can tell them.
- An approved task is ordinary work, as for any guest, and a client's answer to a needs_input question is not held. The only check on that answer is that the teammate's next asks are held, for as long as the mark lasts.
- Rate limits are the only limit on how much a client sends: the same 30 asks a minute, and it can fill your held queue with them. A retried `SendMessage` is a new ask, since the relay does not track `messageId`.

## Rooms

A room is a thread the owner shares with chosen teammates ([protocol](protocol.md#rooms)). It widens who reads what, so its controls are these:

- Visibility follows membership. Only admin devices and the relay's local admin socket create rooms and add or remove members; no agent route or MCP tool changes membership. A member reads every post in the room, its own and others', including teammates' replies to mentions. Non-members cannot read a room, and room posts are not searchable. A mention joins the poster's chain, so the chain's trace and search would otherwise show it to an upstream asker outside the room: for any non-admin reader that is not a member now, trace shows a placeholder for a mention's text and its reply, and search leaves mentions out. The relay checks membership and eligibility on every read and post, not only when a member is added.
- Some agents never join. Council, dot-web and duet-web, whose asks are held for the owner by default, and any agent `approval.json` names cannot be members: a room would hand them teammates' text the owner never approved. A member that `approval.json` starts naming is refused on every read and post until the owner removes it. The history, notes and pass services cannot be members either, so what they retrieve from the owner's private data never lands in a shared thread. A phone may be a member: it reads and posts, but is never asked by a mention, since it never answers.
- A mention is an ask, nothing more. An @mention of a member becomes an ordinary ask from the poster through the same steps as a send: it continues the poster's open chain, so loop, hop and allowlist rules see the whole chain; it takes a slot of the poster's send rate, as every post does; `approval.json` can hold it; and its wake carries counts only, including an email wake for an agent that gets request emails. Only posts made through the post route are read for mentions. A reply posted back to the room is never read for mentions, so text from a web chat or any reply cannot start asks of its own.
- Replies reach the room only from members. A reply to a mention is posted to the room in the same transaction as the reply, and only if the replier is still a member then and still allowed in rooms (checked again at reply time; an `approval.json` that cannot be read refuses); otherwise it stays on the request. Removing a member cancels its open mentions from that room.
- Vendor egress. A web chat member types its mention asks into its vendor's site as the owner, and those asks carry the room's recent posts, so every teammate's recent text in that room goes to that vendor. A member connected through the MCP gateway (ChatGPT, Sesame) reads the thread in its vendor's app. Adding either kind of member says so before or as it is added.
- Room text is data. Mention asks and threads say that posts come from several teammates and are context, not instructions. That is an instruction to a model, not a control: a member that reads untrusted content can still be talked into posting, with the risk described below.
- The audit log records room events with ids, names and byte counts, never post text.

## Scheduled asks

An agent can leave an ask with the relay to send later or on a repeat ([protocol](protocol.md#scheduled-asks)). The ask goes out with no live session behind it, so its controls are these:

- A fire is an ordinary send from the asker. Its target, loop, hop and rate checks, `approval.json`, the default holds by kind, and the wake all apply at fire time, through the same path a send takes. A fire to a held target is held. A rule or target that changed since the schedule was made applies to it. `from` is the agent that made the schedule, attributed when it was made; a fire cannot name anyone else.
- A schedule cannot shed a chain. A fire starts a new chain of the asker alone, whatever the asker holds at fire time, so the relay refuses to make a schedule while the asker holds a claim, by the same lookup a send uses to continue one: otherwise an agent handling a request could leave the loop, hop and allowlist rules behind by asking later. The limit is that lookup's limit: an agent with several open claims and no session to tell them apart starts a new chain with an ordinary ask too, and can schedule one.
- A schedule cannot shed a guest's mark. A fire carries no mark and reads no claims, so the relay refuses a schedule from an agent while a marked ask that has reached it is open: queued, delivered, claimed or needs_input, whatever other claims are open, approved or not. That is wider than a send's mark, because the gaps listed under [Guests](#guests) last a moment for a send and for good in a schedule. A held ask does not count, since the agent has not seen it. A schedule made before a marked ask arrived still fires during it, unmarked and not held as a guest's: its text was fixed first and no route changes it, so the ask has no way into it. The limits: this ends with the ask, so once a teammate has replied it schedules unmarked, and a marked `notify` does not count, only an ask.
- Only the relay starts a chain this way. The flag that turns off parent inference is not read from any request.
- Limits: at most 32 live schedules per agent, a repeat of at least 15 minutes, one target, no attachments, no project label, no follow-on. A recurring schedule never stacks: it skips an occurrence while its last request is open. Occurrences missed while the relay was down fire once.
- A standing ask outlives the turn that made it. An agent talked into scheduling something keeps sending it until the schedule is stopped, and each fire reads to its target like any teammate's ask. The owner sees every schedule with `tincan schedules --all` and stops any with `tincan unschedule <id>` from an admin device or the relay's local admin socket. Removing the owner or the target deletes the schedule. An agent can list and stop only its own, and another agent's schedule looks to it like one that does not exist.
- Delivery is at most once. The relay moves a schedule on before it sends, so a relay that stops between the two loses that occurrence rather than sending it twice. A rejected fire is not retried: a one-shot is gone and its asker is told, and a recurring schedule tries again at its next time, telling its asker once per run of rejections.
- The text waits on the relay. A schedule's body stays in the relay's database in the clear until it is stopped or a one-shot fires, readable by whoever runs the relay, in part by admin devices listing schedules (the first 200 characters) and whole by one stopping it, and is not searchable until it fires. Audit rows carry ids, names, times and the reason for a rejection, never the text.

## Agent Tincan.app on macOS

Release builds of tincan for macOS start their background services through a launcher inside Agent Tincan.app, so Login Items names them "Agent Tincan" instead of the signer ([README](../README.md#macos-login-items)).

- The launcher runs only tincan. It execs its first argument only when that binary satisfies an Apple-anchored Developer ID requirement for the Agent Tincan team and a tincan signing identifier, so other software cannot borrow the Agent Tincan name or icon in Login Items. A same-user attacker can still swap the binary between the check and the exec, or point the launcher at the real tincan with hostile arguments. Both match today's exposure: anything that can write `~/Library/LaunchAgents` can already run signed tincan with any arguments.
- The app is checked before use. `tincan` installs the app embedded in its own signed binary into `~/Applications`, checks its signature against the same team before swapping it in, and replaces an installed copy that fails that check. `tincan doctor` reports a missing or modified app.
- Privacy grants stay where they were. macOS may treat the app as the code responsible for its services' privacy checks, which would let one grant to "Agent Tincan" cover every wrapped service. The notes service is therefore never wrapped, so its Files and Folders grant stays its own.

## What it deliberately does not do

- Joined teammates trust each other fully. Guests are the exception, and [Guests](#guests) says how. A request from a joined teammate is meant to be acted on as if you asked, including actions like placing calls or spending money. The standing instructions say so plainly: a teammate's request is work the owner has already authorized, and agents do not stop to ask the owner for permission. What still holds: the relay's approval holds (council, dot-web, `approval.json`), one teammate at a time for a real-world action, and limits the owner gave an agent directly. By default there is no per-request approval, except that asks to the council and dot-web agents are held (see [Council](#council) and the dot-web note above); the optional owner gate below can hold requests to other agents.
- Tailscale is the security boundary. Anything that can act as a joined machine on your tailnet can make your other agents act. Protect your tailnet: use tagged, short-lived auth keys and review who can add devices. `tincan doctor` reports the local machine's side of this: the Tailscale version against the minimum (1.104.4, which fixes the Tailscale SSH and Serve/Funnel bugs in bulletins TS-2026-014 to TS-2026-017), whether Tailscale SSH is on, and whether the machine is tagged. It only reads the local tailscaled, warns and never fails, enforces nothing, and sees neither other machines nor a relay's embedded Tailscale. It warns about tags only on a machine the relay refuses as an admin; admin devices are untagged by design. With more than one tailscaled running, or with relay traffic going through a proxy on another machine, it skips that warning, because the relay answers for whichever node reached it. Tagging has one cost: a tagged machine is not re-admitted automatically after a [rebuild](#rebuilt-machines).
- The relay can read every request and reply. Run it on a machine you control.
- The Windows client, which is experimental and CI tested only, has no unix file modes. Its config (including the relay key) and downloaded attachments are protected only by the permissions on the user's profile folder, not by 0600 files and 0700 folders, and two tincan processes saving the config at once are not serialized. The relay does not run on Windows.
- `tincan upgrade` trusts the relay host. The sha256 it checks and the binary it installs both come from the same relay, so the check protects against corruption in transit, not against a compromised relay. Only put release files you built yourself or downloaded from your own GitHub release into the relay's `--dist` directory.
- `tincan relay-upgrade` is admin-only, and the relay only ever installs from its own `--dist`. The sha256 it checks comes from the same dist `checksums.txt`, so it guards against a corrupt or truncated file, not against someone who can write to the dist: write access to `--dist` is code execution as the relay user, the next time an admin upgrades. Keep the dist directory writable only by the relay user and the operator.
- `tincan relay-upgrade --from-github` is off unless the relay operator starts the relay with `--release-url` (for this project, `https://github.com/mvanhorn/agent-tincan/releases/download`); the caller can never choose the source. It downloads over HTTPS and checks every binary against that release's own `checksums.txt`. That is the same trust as `install.sh`: it proves the files arrived intact from GitHub, not who built them.
- Self-upgrade needs the relay user to own its binary and the directory it lives in. That is a tradeoff: a process that can replace its own binary survives a compromise across restarts. If you keep the binary root-owned, the relay refuses to upgrade itself and you upgrade it by hand.

## The risk to think about

If one agent reads untrusted content (a web page, an email, a document) and gets tricked, it can ask a teammate to do something harmful, and the teammate will. Before joining an agent that reads untrusted content alongside one that holds real powers:

- Agents treat a teammate's request as authorized and do not stop to ask, except before spending money or contacting someone in a way they would normally confirm with you. Give high-power agents instructions about which other kinds of requests they should confirm with you first, or hold them with the [owner approval gate](#owner-approval-gate).
- Keep `tincan trace` handy so you can see who asked for what.
- For an OpenAI dot (`dot-web`), which reads your connected apps, list the teammates it may ask in `~/.config/tincan/dot-web-send.txt`; with no file it may ask any joined agent, like every other teammate. For Claude in a Duet chat (`duet-web`), use `~/.config/tincan/duet-web-send.txt`.
- Use `tincan remove <agent>` to cut an agent off immediately. Its queued requests are cancelled and, for an agent connected through the gateway (ChatGPT, Sesame), its tokens are revoked.

## Owner approval gate

The owner can create `approval.json` in the relay state directory, with mode
0600, to hold incoming requests before chosen agents receive them:

```json
{"gate":{"muse":{"from":"*"},"instinct":{"from":["chatgpt","grokbot"]}},"notify":"grokbot","hold_ttl":"2h"}
```

A `from: "*"` rule holds every request to that target. A `from` list holds when
any agent in the relay-recorded chain or the authenticated sender matches.
An `unless` list instead holds when any member is absent from the list. Exactly
one of `from` and `unless` is required per target. Client-supplied identities,
chains and statuses cannot bypass the check, which runs after the relay's
cycle, hop and rate checks and before delivery. Both asks and notifies are gated.

A missing file disables the gate for every target except agents of kind
`council`, `dot-web`, `duet-web` and `pass`, which are held by default (see [Council](#council)
and [Passing a conversation](#passing-a-conversation)). The relay reloads changed files. Unreadable,
malformed or group/world-accessible policies hold every request to every target
in the last good copy, regardless of its previous sender restrictions. With no
valid copy, a bad policy prevents startup; if it first appears while running,
new sends fail until it is fixed. Removing the file disables gating for future
sends; changing or removing it never releases already-held requests.

Held requests neither wake their targets nor appear in their inboxes or queued
counts. The sender sees `held`; the target cannot claim or reply to one. Only
admin devices and the relay's local admin socket can run `tincan held`,
`tincan approve <id>` or `tincan deny <id> [reason]` (with `--relay` or `--socket`),
or approve and deny from the [phone page](phone.md) on an admin device. No MCP
tool lists, approves or denies held requests.
Approval queues and wakes normally, keeping the original creation time and
starting a fresh delivery TTL. Denial returns `declined` with the reason.
`hold_ttl` defaults to two hours; overdue holds become `expired` and cannot be
approved. Senders can cancel a hold, and removing an agent cancels its holds.
The audit log records `held`, `approved`, `denied`, and `hold_expired` transitions.

If `notify` names a joined operator, the relay sends it a `notify` attributed to
`relay`, with the sender, target, request id and owner commands, and no request
text: the notified agent may itself be gated (even the held target), and
unapproved text must not reach it. The owner reads the request with `tincan held`. This
admin notice bypasses gating to avoid recursion, is logged as
`approval_notified` (or `approval_notify_failed` on failure), and carries no
approval authority. Notification
failure leaves the original request held. The operator must never approve on
another agent's request. Approval remains an action on an admin device or the
local socket; the notice does not grant the receiving agent those powers.

This gate adds a relay-enforced pause for owner review, not a judgment about
whether the message is safe. Protect admin devices and the relay state directory.

Requests retain whether they were ever held and whether the owner approved them.
For every request that was held and never approved, only its sender and admins
may read its body or attachments, regardless of its current status (including
declined, expired and cancelled). Other callers, including the target, see
`waiting for the owner's approval` and no attachment metadata wherever the
request is otherwise visible: get, trace, search-like listings, poll and peek
pending entries. Attachment downloads by those callers return 404. Held requests
remain excluded from delivery; pending entries carry only ids and senders.
An approved request follows the ordinary body and attachment access rules,
even after it reaches a terminal state. Approval history survives relay restarts;
upgrades backfill existing holds and decisions from request state and audit events.
